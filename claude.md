# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What HttpMultipart is

A **source-only** NuGet package for reading and writing HTTP multipart content. The package ships `.cs`
files, not an assembly: they compile into the consuming project, so there is no runtime dependency and
the types stay `internal` to whoever compiled them.

The reader is vendored from `dotnet/aspnetcore`'s `Microsoft.AspNetCore.WebUtilities` (MIT) with its
two package dependencies stripped out. It was extracted because `BlazorQL` and `Scry` each carried a
private copy that had already started to drift.

**Neither consumer has been migrated yet** — that waits on a nuget.org release. When it happens:
`BlazorQL` deletes `src/BlazorQL/Fetchers/Multipart/`; `Scry` deletes the six shared files from
`src/Scry.Client/Multipart/` (keeping its own `MultipartResponse.cs`) and `src/Scry.Server/
MultipartWriter.cs`. Both then add `<PackageReference Include="HttpMultipart" PrivateAssets="all" />`.
Scry's `InternalsVisibleTo Scry.Explorer.Core` keeps working: source-only types compile into
`Scry.Client` and stay internal to it. The API here is shaped so neither needs source edits beyond
optionally collapsing their duplicated boundary/byte-reading glue onto `TryGetMultipartBoundary` and
`ReadAsBytesAsync`.

## Build and test

```bash
dotnet build src/HttpMultipart.slnx -c Release
dotnet test src/HttpMultipart.slnx -c Release --no-build
pwsh src/verify-package.ps1
```

`verify-package.ps1` packs and then builds the `Consume*` projects against the real `.nupkg`. It is the
only thing that exercises the nuspec, and it is **not** part of the solution build — the Consume
projects restore a package that does not exist until pack has run.

## Layout

- **`src/HttpMultipart/`** — the package project. Every `.cs` file directly in this folder ships.
  - `HttpMultipart.nuspec` — a hand-written nuspec with a `<files>` allowlist. The allowlist never
    mentions `lib/`, which is how the compiled assembly stays out of the package. The project is
    compiled only to type-check the sources.
  - `build/HttpMultipart.props` — adds the `HttpMultipart` global using to consumers.
  - `build/HttpMultipart.targets` — the `net10.0` guard and the Solution Explorer hider.
  - `obj/pack/` — generated. The `StageSource` target copies each source file here prepending
    `// <auto-generated />`, `#pragma warning disable`, `#nullable enable`. Never edit these; the
    nuspec ships them rather than the authored files so consumers with strict analyzer settings are
    not broken by our source.
- **`src/Tests/`** — NUnit. Links the sources and imports the package's own `.props`/`.targets`, so a
  test run exercises the consumer's MSBuild logic without a pack step.
- **`src/Consume*/`** — compile-only projects that restore the packed `.nupkg`. Deliberately outside
  the solution. `Consume` (implicit usings on), `ConsumeNoImplicitUsings` (explicit using),
  `ConsumeOldTfm` (asserts the TFM guard fires).

## Constraints that are easy to break

- **`ImplicitUsings` is disabled** and `ProjectDefaults` is referenced with
  `ExcludeAssets="contentFiles"` in the package project. Both exist so the shipped sources must carry
  every `using` they need. Do not "tidy" either away — a consumer has neither.
- **`Cancel` is not available** in `src/HttpMultipart/`. The package project removes the alias
  `ProjectDefaults` injects, because a consumer will not have it. Spell `CancellationToken`.
- **The types are in `namespace HttpMultipart`**, not the global namespace. A global-namespace
  `MultipartReader` would silently win name lookup over `Microsoft.AspNetCore.WebUtilities`'s in an
  ASP.NET Core consumer.
- **Error message strings are asserted verbatim** by the ported tests, and match aspnetcore's. Changing
  one is a breaking change for anyone matching on it.
- Line endings are **LF**.

## Tests

- `MultipartReaderTests` / `BufferedReadStreamTests` — ported from aspnetcore, upstream method names
  kept so the files can be diffed against upstream when it grows a test.
- `MultipartConformanceTests` — RFC 2046 edge cases upstream does not reach, plus the two places this
  reader deliberately differs (single-valued headers, no `BaseStreamOffset`).
- `MultipartRoundTripTests` — writer output fed back through the reader. Neither upstream repo has
  this, and it is what pins the two halves against each other.
- `Usage.cs` — the readme's examples, as tests. `#region` names are snippet ids; building `Tests`
  regenerates the snippet regions in `readme.md`. Never hand-edit inside them.

## Releasing

`<Version>` in `src/Directory.Build.props` is for local builds only. Pushing a tag runs
`.github/workflows/release.yml`, which takes the version from the tag name (`1.2.3` or `v1.2.3`) and
publishes via nuget.org trusted publishing — no stored API key.
